# Phase 12 Post-Closure AI Runtime Reliability Investigation
## Root Cause Analysis Report

**Document Reference:** `PHASE-12-AI-RCA-001`  
**Application:** Lead Intelligence Agent  
**Environment:** Local Ollama (`http://127.0.0.1:11434`), Model: `qwen2.5-coder:latest` (7.6B Parameters, CPU Execution), Windows 11  
**Investigation Date:** 2026-11-05  
**Audit Status:** COMPLETE  

---

### Executive Summary

During Phase 12 post-closure operational verification, the application user interface reported runtime failures across all three core AI services:
1. **AI Sales Intelligence:** `The selected AI provider could not generate valid sales intelligence. TIMEOUT`
2. **AI Recommended Actions:** `The response did not meet current evidence validation.`
3. **AI Proposal Intelligence:** `The selected AI provider could not generate a valid proposal brief.`

Crucially, the automated test suite reported **1,094/1,094 passing tests** prior to runtime discovery. This investigation identifies the foundational divergence between mock test assertions and production AI runtime behavior, analyzes the exact programmatic and architectural root causes for each defect, and details the performance profile of local CPU-bound language models.

---

### Why the 1,094 Automated Tests Did Not Catch These Failures

The automated test suite in Phase 12 executed against mocked AI providers (`MockAIProvider`) that instantly returned pre-crafted, synthetically compliant JSON payloads. This design masked four critical runtime failure modes:

| Test Assumption vs. Real Runtime Reality | Mock Test Suite | Real Ollama Runtime |
| :--- | :--- | :--- |
| **Execution Latency** | 0.001 seconds (synchronous in-memory return) | 60–180+ seconds (CPU-based token generation) |
| **Schema Grammar Compilation** | Never parsed (returns raw dict) | Compiles GBNF grammar on every HTTP request |
| **Prompt Token Density** | Unmeasured | Heavy context balloons prompt evaluation time to 50–70s |
| **Lead State Edge Cases** | Mocked leads with explicit `priority="HIGH"` | Unprioritized leads with `lead.priority is None` |
| **Model Output Stochasticity** | Perfect schema alignment guaranteed by mock | Missing top-level redundant lists, UUID listing spam |

Because unit tests never exercised live inference against the local Ollama provider, structural schema bugs and latency timeouts were completely invisible to CI/test runners.

### Deep Dive: Defect 1 — AI Sales Intelligence Timeout

#### Observed Behavior
When requesting AI Sales Intelligence for a lead in the UI, the operation stalled for 300 seconds and returned:
`The selected AI provider could not generate valid sales intelligence. TIMEOUT`

#### Root Cause Analysis
1. **Excessive Output Token Ceiling:**
   `generate_ai_sales_intelligence()` in `backend/app/services/ai_sales_intelligence.py` had configured `max_output_tokens=5000`. On a CPU-bound Ollama instance running `qwen2.5-coder:latest`, token generation operates at **2.2 to 2.8 tokens per second**. If the model generated 1,000–1,500 tokens of verbose analytical prose across summary, insights, opportunities, and actions, generation alone took **350 to 550 seconds**, directly breaching `request_timeout_seconds=300`.
2. **Heavy Input Context Evaluation Latency:**
   The prompt payload generated by `AISalesContextBuilder` serializes the full lead facts, catalog snapshot, SEO audit summaries, and outreach history (~1,800 to 2,500 prompt tokens). On local CPU execution, Ollama processes prompt tokens at ~35 tokens per second, introducing an upfront **50 to 70 second prompt evaluation latency** before the first output token is generated.
3. **Missing Section Size Directives:**
   The system prompt lacked explicit size bounds (e.g., "Select 1 to 3 items per section"), prompting the LLM to provide multi-paragraph explanations for every opportunity and recommendation.
4. **Top-Level `evidence_refs` Discrepancy:**
   Even when the LLM returned complete nested evidence citations inside each section (`summary.evidence_refs`, `insights.evidence_refs`), Ollama occasionally omitted or emptied the redundant top-level `evidence_refs: []` list. This caused Pydantic schema validation failure or cross-field validation rejection.

### Deep Dive: Defect 2 — AI Recommended Actions Evidence Validation Failure

#### Observed Behavior
When generating recommended actions for an unprioritized lead, the backend logged:
`AIValidationError: Action priority HIGH does not match lead priority None`
and returned to the UI:
`The response did not meet current evidence validation.`

#### Root Cause Analysis
1. **Unprioritized Lead Priority Comparison Bug:**
   In `backend/app/services/ai_sales_action_planner.py`:
   ```python
   # Defective code:
   if action.priority.value != lead.priority:
       raise AIValidationError(
           f"Action priority {action.priority.value} does not match lead priority {lead.priority}"
       )
   ```
   In the database schema, `Lead.priority` is nullable. When a lead is newly imported or unprioritized, `lead.priority` is `None`. However, `ActionPriority` enum is closed (`HIGH`, `MEDIUM`, `LOW`). Because the LLM must choose an enum value (defaulting to `MEDIUM` or `HIGH`), `action.priority.value != None` evaluated to `True` for every unprioritized lead, throwing an immediate `AIValidationError`.
2. **Defective `ACTION_SOURCE_TYPES` Whitelist:**
   `validate_action_plan` strictly enforces that every cited evidence ID originates from an allowed source type registered in `ACTION_SOURCE_TYPES`. The original map omitted `"lead"` from several actions (e.g., `CALL_PROSPECT`, `REVIEW_SEO_OPPORTUNITY`), and omitted valid commercial/opportunity sources (`"seo_opportunity"`, `"deterministic_service_recommendation"`, `"lead_intelligence_opportunity"`) from `FOLLOW_UP` and `CALL_PROSPECT`. When the LLM cited the lead's company record or SEO opportunity for a follow-up action, the planner threw an `AIValidationError`.
3. **Token Inflation via Evidence ID Enumeration:**
   When an un-enriched lead has multiple missing fields (`website`, `phone`, `email`, `linkedin`, etc.), the context builder creates 10 distinct `missing_data` markers, each assigned a 55-character UUID reference. Without explicit constraints, `qwen2.5-coder` enumerated all 10 missing data UUID strings into `evidence_ids`, consuming >320 tokens on UUIDs alone and triggering timeouts.

### Deep Dive: Defect 3 — AI Proposal Intelligence Generation Failure

#### Observed Behavior
When invoking Proposal Intelligence, the UI reported:
`The selected AI provider could not generate a valid proposal brief.`
Inspection of backend logs revealed schema parsing errors and execution timeouts.

#### Root Cause Analysis
1. **Redundant Schema Duplication in Prompt:**
   In `backend/app/services/ai_proposal_intelligence.py`, the code constructed the request payload as:
   ```python
   # Defective payload construction:
   payload = {
       "lead": context["lead"],
       ...
       "selection_schema": ProposalSelection.model_json_schema(), # Injected 5,158 characters!
   }
   ```
   At the same time, the `AIRequest` passed `response_schema=ProposalSelection.model_json_schema()` to `OllamaProvider`, which translates the schema into an Ollama GBNF grammar (`format=schema`).
   Injecting 5.2 KB (~1,200 tokens) of repetitive JSON schema into the user prompt doubled prompt evaluation time, consumed substantial CPU memory, and confused the model by presenting two overlapping schema representations.
2. **Grammar Compilation & Generation Stall:**
   Ollama's GBNF grammar parser took an additional 3–5 seconds to compile the deeply nested schema. Combined with `max_output_tokens=3000`, the generation exceeded local execution thresholds.
3. **Evidence Reconciliation Failure & Provider-Layer Validation Boundary:**
   The `ProposalSelection` contract requires a top-level `evidence_refs: list[str]` that must exactly match the set-union of all nested item citations. Small language models (7B) cannot reliably construct mathematically identical set-unions across multiple nested JSON keys directly during single-pass autoregressive generation.
   Crucially, `parse_structured()` in `backend/app/providers/ai_http.py` executes `model_validate()` directly on the raw provider string before passing control back to the calling service, raising `AIProviderOutcome.INVALID_STRUCTURED_OUTPUT` before service-level reconciliation can execute.
